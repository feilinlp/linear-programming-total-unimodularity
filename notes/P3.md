## 1. The three algorithms (section 6)

The order is **chronological**, not the order in the lecture list, because each algorithm answers the weakness of the one before:

> **Simplex** (fast in practice, exponential worst case) → *"is LP polynomial at all?"* → **Ellipsoid** (yes, but slow in practice) → *"can we have both?"* → **Interior point** (polynomial and fast).

### 1.1 Simplex (Dantzig, 1947)

**How it works.** From L7: a bounded feasible LP has an optimal **vertex**. Simplex starts at a vertex and repeatedly moves along an edge to a **neighbouring vertex with a better objective** (a *pivot*: one variable enters the basis, one leaves). It stops when no neighbour is better. By convexity that vertex is optimal. Each vertex is a basic solution x_B = A_B⁻¹b.

**Time complexity.**
- Each pivot is cheap (polynomial).
- **The number of pivots can be exponential.** Klee and Minty (1972) built a slightly squashed n-dimensional cube (n variables, n constraints plus x ≥ 0) where simplex with Dantzig's rule (enter the variable with the largest reduced cost) visits **all 2ⁿ vertices: 2ⁿ − 1 pivots**. We checked this with our own textbook implementation for n = 2…12: exactly 3, 7, 15, …, 4095 pivots. Similar examples exist for most other pivot rules. **No pivot rule is known to be polynomial.**
- **In practice it is fast**, typically a small multiple of m pivots. Spielman and Teng (2001) explained why with *smoothed analysis*: if the input is perturbed by a little random noise, the expected number of pivots is polynomial. Klee–Minty-type inputs are fragile.

**Example to keep in mind:** the Klee–Minty cube for n = 3 on the slide. The path visits all 8 corners: 7 pivots.

### 1.2 Ellipsoid method (Khachiyan, 1979)

**How it works.** Start with a huge ellipsoid E₀ guaranteed to contain the feasible region (or an optimal point). Repeat:
1. Check the **centre** of the current ellipsoid. If it is feasible (and good enough), done.
2. Otherwise find a **violated constraint** aᵢᵀx ≤ bᵢ. The feasible region lies entirely on one side of the parallel hyperplane through the centre.
3. Replace the ellipsoid by the **smallest ellipsoid containing that half**.

Each step shrinks the **volume by a factor of about e^{−1/(2(n+1))}**. Since a non-empty feasible region cannot have arbitrarily small volume (bounded using L), the method must stop after polynomially many steps. Optimisation is reduced to feasibility, for example by adding cᵀx ≥ value and doing binary search, or by using objective cuts.

**Time complexity.** **O(n²L) iterations** of O(n²) arithmetic each, so **O(n^4 · L) arithmetic operations** on O(L)-bit numbers (for m = O(n)). Here L = number of bits needed to write down A, b, c. This made Khachiyan's result the **first proof that LP is in P**.

**Why it is slow in practice.** It typically needs close to its worst-case number of iterations, and its numerics are delicate. Nobody uses it to solve LPs.

**Why it still matters.** It never needs the full constraint list, only a **separation oracle** (given x, either say it is feasible or return one violated constraint). Grötschel, Lovász and Schrijver (1981) used this to show that LPs with **exponentially many constraints** can be solved in polynomial time if separation is easy. In theory, optimisation and separation are equivalent.

### 1.3 Interior point methods (Karmarkar, 1984)

**How it works.** Instead of walking on the boundary, move through the **interior** of the polytope. Modern *path-following* methods add a **barrier** term −μ Σ log(slackᵢ) to the objective, which blows up near the boundary and keeps iterates inside. For each μ there is one minimiser; as μ → 0 these points trace the **central path**, which leads to an optimal solution. Each iteration takes one Newton step (one linear system solve) and then decreases μ.

**Time complexity.** Karmarkar: **O(n^3.5 · L) arithmetic operations** (for m = O(n)). Path-following methods (Renegar 1988) need **O(√n · L) iterations**, each about O(n³). **In practice:** usually 20–60 iterations, almost independent of problem size. This is why solvers such as HiGHS, Gurobi and MOSEK include it.

**The catch for our project.** The iterates never touch the boundary, so the method converges to the **centre of the optimal face**, not to a vertex (Güler–Ye 1993). If the optimum is unique, that is a vertex. If optima are **tied**, it can be a fractional point. **Crossover** (Megiddo 1991) moves the answer to an optimal vertex afterwards.
- Pilot check (HiGHS 1.15.1, VC LP on C₄): interior point without crossover returned (½,½,½,½). With crossover it returned (1,0,1,0), and dual simplex returned (0,1,0,1). Same on K₃,₃.

### 1.4 Summary table

| | Simplex | Ellipsoid | Interior point |
|---|---|---|---|
| Year | 1947 | 1979 | 1984 |
| Moves | along edges, vertex to vertex | shrinking ellipsoids around the region | through the interior along the central path |
| Worst case | exponential (Klee–Minty, 2ⁿ − 1 pivots) | O(n^4 · L) | O(n^3.5 · L) |
| In practice | fast | slow | fast |
| Returns a vertex? | always | n/a (theory only) | not necessarily; needs crossover |

### 1.5 Background for questions

- **Weakly vs strongly polynomial.** "Polynomial in L" depends on the number of **bits** of the input. This is the same idea as Lecture 6, where Ford–Fulkerson's Θ(mC) is *not* polynomial because C takes only log C bits. Ellipsoid and interior point are only *weakly* polynomial: their time grows with L. **Tardos (1986):** if A has small integer entries, the LP can be solved in time depending only on A, not on b and c. TU matrices have entries in {0, ±1}, so **TU LPs are solvable in strongly polynomial time.**
- **Dual simplex** (Lemke 1954), HiGHS's default, keeps the objective "optimal-looking" (dual feasible) while it fixes infeasibility. It still moves between bases, so it also ends at a vertex, and is integral on TU instances.
- **Open problem:** is there a strongly polynomial algorithm for general LP? (Smale's 9th problem.) Is there a polynomial pivot rule for simplex?

## 2. The experiments (section 8)

The trailer presents **plans, not results**. For each experiment: why it is there, the setup, and what the theory predicts. The group plan says to commit to 1–2; **agree the final set with the group.** E5 (Klee–Minty pivot counts) is left out of the trailer for now.

### E1: Is TU necessary?
- **Why:** P1's theorem says TU ⇒ the LP is exact. E1 asks the converse: does the LP need TU to be exact? TU guarantees an exact LP for *every* right-hand side and objective, but a particular non-TU instance can still be exact. So **TU is sufficient but not necessary**.
- **Example (checked in HiGHS):** a square (C₄) plus one diagonal. The diagonal creates a triangle, so the incidence matrix contains the triangle's 3×3 submatrix with determinant 2 and is not TU. Yet simplex returns (1,0,1,0) with LP = ILP = 2.
- **Subtlety:** (½,½,½,½) is also an optimal vertex of that LP; simplex happened to return the integral one. So measure "LP value = ILP value" and "returned answer is integral" separately.
- **Setup:** random non-bipartite graphs (networkx, e.g. Erdős–Rényi graphs, checked with `nx.is_bipartite`). Solve the **VC LP** with HiGHS simplex and the **ILP** with HiGHS branch-and-bound as ground truth.
- **Measure:** % of graphs with LP value = ILP value; % with an integral returned answer; size of the gap when they differ.
- **Predict:** a clear share of non-bipartite graphs is still exact, so TU is not necessary. When the LP is not exact, the fractional values are ½ (Nemhauser–Trotter 1975).

### E2: How costly is recognising TU?
- **Why:** connects to P2's slide. Recognising TU is the practical bottleneck before trusting the LP.
- **Setup:** TU matrices (e.g. bipartite incidence and interval matrices) and non-TU matrices of growing size. Compare brute force over all square submatrices, the Ghouila-Houri row-signing test, and the Seymour-decomposition test in the CMR library.
- **Measure:** runtime vs matrix size.
- **Predict:** brute force and Ghouila-Houri grow exponentially; CMR grows polynomially.

### E3: Does the LP algorithm matter? (follows from section 6)
- **Why:** TU guarantees integral **vertices**, not integral optimal **points**. We want to see whether the solver choice decides if we actually get an integer answer.
- **Setup:** TU instances with **tied optima**: even cycles C₂ₖ, complete bipartite K_{n,n}, grid graphs. Solve with HiGHS dual simplex, interior point with crossover, and interior point without crossover (`highspy`, `run_crossover = "off"`).
- **Measure:** % of runs that return an integral solution.
- **Predict:** simplex and interior point with crossover always integral; interior point without crossover fractional (centre of the optimal face) whenever optima tie.

### E4: Generic LP or specialised algorithm?
- **Why:** connects to P4's applications and Lectures 4–6. On TU problems a generic LP solver and a specialised combinatorial algorithm both return the exact optimum. E4 compares them head to head: same answer, how different in speed?
- **Setup:** max-flow and bipartite matching instances of growing size. Compare the HiGHS LP against Dinic (max-flow) and Hopcroft–Karp (matching) from networkx.
- **Measure:** runtime; check that both reach the same optimum.
- **Predict:** same optimum (integrality theorem, L6); the specialised combinatorial algorithms are faster.

**Tools:** Python, `highspy`, networkx, CMR. All code and data in this repo (`experiments/`).
